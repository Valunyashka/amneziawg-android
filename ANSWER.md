Реализация двойного туннелирования напрямую в кодовой базе `amneziawg-android` (и `amneziawg-go`) — это фундаментальная переработка архитектуры приложения, которая затрагивает сразу несколько слоев: Go-ядро, JNI (C-биндинги), Java/Kotlin Backend и UI.

Ниже описан высокоуровневый план (концепт) того, как это должно быть реализовано.

### Архитектурный подход
Поскольку `VpnService` в Android может захватывать трафик только в один файловый дескриптор `tun`, нам нужно реализовать первый туннель полностью в пользовательском пространстве (user-space / netstack), а второй туннель — как системный, пустив его пакеты через первый.

### 1. Изменения в слое Go (`tunnel/tools/libwg-go/api-android.go`)
Текущая реализация (через `conn.NewDefaultBind()`) использует стандартные системные сокеты Android.
Чтобы пустить один туннель (Туннель 2) через другой (Туннель 1):

1. **Создание виртуального стека (Netstack):**
   Туннель 1 не должен создавать `VpnService`. Вместо этого мы должны использовать библиотеку `gvisor.dev/gvisor/pkg/tcpip` (или `golang.zx2c4.com/wireguard/tun/netstack`), чтобы создать виртуальный сетевой интерфейс в памяти.

2. **Кастомный `conn.Bind` для Туннеля 2:**
   Туннелю 2 (который связан с Android `VpnService` и `tun` дескриптором) нужно передать кастомный `Bind`. Этот `Bind` будет отправлять зашифрованные UDP-пакеты не в системную сеть `conn.NewDefaultBind()`, а *внутрь виртуального стека Туннеля 1*.

```go
// Концептуальный код для api-android.go

import (
	"golang.zx2c4.com/wireguard/tun/netstack"
	"github.com/amnezia-vpn/amneziawg-go/conn"
	"github.com/amnezia-vpn/amneziawg-go/device"
)

// 1. Поднимаем Туннель 1 (Программный)
tun1, tnet, err := netstack.CreateNetTUN(...)
dev1 := device.NewDevice(tun1, conn.NewDefaultBind(), ...)
dev1.IpcSet(tunnel1Config) // Подключились к Серверу 1

// 2. Создаем кастомный Bind для Туннеля 2, который будет маршрутизировать UDP через tnet (Туннель 1)
type ProxyBind struct {
	net *netstack.Net
}
// Реализация методов conn.Bind (Open, Close, Send, Receive),
// использующих tnet.DialUDP() вместо net.ListenUDP()

// 3. Поднимаем Туннель 2 (Системный, связанный с Android VpnService fd)
dev2 := device.NewDevice(androidTunFD, &ProxyBind{net: tnet}, ...)
dev2.IpcSet(tunnel2Config) // Подключились к Серверу 2 через Сервер 1
```

### 2. Изменения в слое Java / JNI (`tunnel/src/main/java/.../Backend.java`)
Вам потребуется изменить JNI-мост (`jni.c` и `api-android.go`), чтобы метод `wgTurnOn` принимал **две** конфигурации вместо одной.
В Java-коде придется переписать класс `GoBackend.java`, чтобы он парсил и передавал обе конфигурации.

### 3. Изменения в UI и Базе Данных
Текущая база данных и UI рассчитаны на модель `1 Профиль = 1 Сервер`.
Придется:
- Изменить схему БД (Room) для хранения связей (какой профиль является "внешним", а какой "внутренним").
- Добавить в UI экрана редактирования туннеля опцию "Использовать прокси-туннель" и выбор второго профиля из списка.

### Итог
Чтобы реализовать это в текущем репозитории, потребуется написать сотни строк кода на Go (для интеграции `netstack` и кастомного UDP-биндинга), переписать JNI-мост и значительно изменить UI и архитектуру БД Android-приложения.

Самый реалистичный и быстрый способ сделать это "для себя" без переписывания всего UI — это жестко захардкодить настройки "Туннеля 1" прямо в `api-android.go` и использовать `netstack` для проксирования пакетов основного `VpnService` туннеля через него.
